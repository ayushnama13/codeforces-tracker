## Feature ideas for our tracker

1. **Solve-probability practice tiers** — Offer target problems at calibrated easy/medium/hard chances of success (for example, 80/50/20%), and let the user hide solved or recently attempted items. Inspired by AtCoder Problems recommendations. Data needed: `problemset.problems`, `user.status`, `user.info`; probability calibration is a local model.
2. **Daily effort and active-day calendar** — Add a calendar heatmap with separate views for submissions, first-time ACs, and hardest rating solved each day. Inspired by AtCoder Problems progress and LeetCode/CodeChef cards. Data needed: `user.status`.
3. **Per-language success and streak report** — Compare accepted counts, attempt counts, and current/longest streak by language to spot where a language slows practice. Inspired by AtCoder Problems language progress. Data needed: `user.status`.
4. **Contest-series performance profiles** — Compare outcomes across contest types or series (e.g., Div. 2 vs Div. 3, educational, global rounds) rather than grouping all contests together. Inspired by AtCoder Analytics' series breakdown. Data needed: `contest.list`, `contest.standings`, `user.rating`.
5. **Untouched versus failed problem coverage** — For each rating band and tag, separate never-attempted problems from attempted-unsolved and solved problems, showing the archive's coverage denominator. Inspired by AtCoder difficulty/category progress pies. Data needed: `problemset.problems`, `user.status`.
6. **Problem difficulty confidence and provenance** — Show official rating plus a confidence/uncertainty indicator, distinguishing contest-derived ratings from unrated or weakly estimated problems. Inspired by zerotrac and the LeetCode difficulty extension. Data needed: `problemset.problems`, external (optional estimated-rating dataset).
7. **Attempt-path review by problem** — Expand a problem into its chronological verdicts, elapsed time to AC, language, and whether it was solved in contest or practice. Inspired by CodeChef's per-day problem drilldown and LeetCode contest question timing. Data needed: `user.status`, `contest.standings`.
8. **Contest expected-versus-actual result** — For each contest, compare rank/solved count with expectation based on the user's rating and the field, including provisional uncertainty. Inspired by CodeChef Elo-MMR explanations and LeetCode contest predictors. Data needed: `contest.standings`, `user.rating`, `user.info`.
9. **Live contest solve milestones** — Plot cumulative solves and rank changes at elapsed-time checkpoints, then compare them to the user's historical contest pace. Inspired by elogrit's live rank curves and solve milestones. Data needed: `contest.standings`.
10. **Difficulty-weighted solve points** — Track cumulative weighted progress, such as rating points solved or progress by rating-color tiers, alongside raw solve count. Inspired by AtCoder rated-point sum and difficulty-colored progress charts. Data needed: `problemset.problems`, `user.status`.
11. **Problem selection by predicted time budget** — Recommend a small set of problems that fits a chosen session length, using the user's historic solve time by rating and tag to estimate duration. Inspired by timed AtCoder virtual contests and LeetCode question timing. Data needed: `user.status`, `problemset.problems`; external input for user-entered session budget.
12. **Problem exposure funnel** — Show each tag/rating cell as counts of unseen, attempted, and accepted problems, so low solve counts can be distinguished from limited exposure. Inspired by AtCoder's AC/non-AC/no-submission progress pies. Data needed: `problemset.problems`, `user.status`.
13. **Shareable analytics card export** — Generate a compact SVG/PNG report with configurable metrics and date range for a profile or training log. Inspired by LeetCard, LeetCode Profile Generator, and CodeChef Stats API cards. Data needed: `user.info`, `user.rating`, `user.status`.
14. **Peer comparison with normalized rates** — Compare tag/rating coverage and contest outcomes against one or more chosen peers, normalizing by total attempts or number of contests. Inspired by SPOJ user statistics and LeetCode Contest Stats. Data needed: `user.status`, `user.rating`, `user.info`; peer handles supplied by user.
